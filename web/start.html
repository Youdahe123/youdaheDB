Get started

Clone it, build it, and write your first durable key in about two minutes. No package manager, no config file, no dependencies to resolve.

FIRST — THE HONEST PART

What actually works today

This is an early project being built in public. Rather than let you find out by trial and error, here is exactly what runs right now:

capabilitystatusnotes
Write-ahead logworking fsync on every write, replays on startup
Memtableworking sorted, tombstones, flush threshold
SSTable writerworking flush, open, get — not yet reachable from the REPL
Interactive REPLworking put · get · delete · scan, survives restarts
LSM read pathnext up src/lsm.rs — reads still only see the memtable
Compactionplanned M1 · issue #4
Server, SQL, clusterplanned M3–M7 — the CLI and console run on mock data until then
STEP 1

Install

You need a Rust toolchain. That is the entire dependency list — Cargo.toml has an empty [dependencies] section and it stays that way.

terminalcopy
$ git clone https://github.com/Youdahe123/youdaheDB.git
$ cd youdaheDB
$ cargo build --release
   Compiling youdaheDB v0.1.0
    Finished release [optimized] target(s)
STEP 2

Run the REPL

The binary starts an interactive shell. Every write goes to the write-ahead log and is fsynced before it is acknowledged, so an accepted write is on disk.

terminalcopy
$ cargo run
youdaheDB v0.1
commands: put <key> <value> | get <key> | delete <key> | scan | quit

db> put user:1 youdahe
OK
db> put user:2 ada
OK
db> get user:1
youdahe
db> delete user:2
OK
db> get user:2
(deleted)
db> scan
  user:1 = youdahe
  user:2 (deleted)

get user:2 returning (deleted) rather than (not found) is deliberate — a tombstone has to be distinguishable from a miss, or a delete would be undone by an older value sitting in an SSTable underneath it.

STEP 3

Prove the durability claim

Do not take the word "durable" on faith — kill the process without a clean shutdown and watch the log replay.

terminalcopy
# in another terminal, while the REPL is running:
$ pkill -9 youdaheDB

# then start it again
$ cargo run
recovered 2 entries from WAL
youdaheDB v0.1

db> get user:1
youdahe   ← still there after SIGKILL

The data file is data.wal in the working directory. Delete it and you start clean. Automating this loop is issue #13.

STEP 4

Use the CLI

The client is a psql workalike. It is scriptable, pipe-friendly, and returns real exit codes — 0 ok, 1 query error, 2 connection error.

terminalcopy
# interactive
$ ./cli/youdahedb
youdahedb=# \dt
youdahedb=# select id, email from users limit 3;

# one-shot, for scripts and CI
$ ./cli/youdahedb -c "select count(*) from orders"

# from a pipe
$ echo "select 1" | ./cli/youdahedb

# point at another node
$ ./cli/youdahedb --host 10.0.1.11 --port 8080
Running on mock data. The CLI speaks the HTTP API in web/API.md, which no server implements yet. Until issue #19 lands it falls back to an in-process mock so the command surface can be designed and used first. It prints a warning on startup so you always know which one you are talking to.
STEP 5

Open the console

A browser console for the whole database — SQL shell, schema, cluster nodes, ranges, transactions, LSM storage, jobs and metrics.

terminalcopy
$ python3 -m http.server 8777 --directory web
# then open http://127.0.0.1:8777/console.html

Every view carries a badge saying whether it is live, partly wired or planned, with links to the issues that would make it real. Nothing in there pretends to be finished.

STEP 6

Embed the engine

The storage engine is a library first and a server second. This is the API that issue #3 introduces.

rustcopy
use youdahedb::LsmTree;

fn main() -> std::io::Result<()> {
    // opens the dir, loads SSTables newest-first, replays the WAL
    let mut db = LsmTree::open("./data")?;

    db.put("user:1", "youdahe")?;
    let v = db.get("user:1")?;
    db.delete("user:1")?;

    // sorted iteration across memtable + every SSTable
    for (k, v) in db.scan("user:".."user;") {
        println!("{k} = {v}");
    }
    Ok(())
}
Not yet on crates.io. LsmTree is the next thing being built — today main.rs drives the WAL and memtable directly and SSTables are not reachable from it.
